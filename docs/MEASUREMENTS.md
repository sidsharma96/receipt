# Measuring Receipt without guessing

Phase 6, implemented 9 October 2026. Diagnostics are opt-in; no exporter, external
service, dependency installation or deployment is required. These records are
not a durable audit trail and do not attribute uploads to a person.

## Find one request

Run the server with `--request-log` in addition to its normal configuration.
Each response has an `X-Receipt-Request-ID` generated by the server. Find that ID
in stderr to see the operation, status, handler duration and measured stages.
Incoming request-ID headers are ignored. IDs combine a random namespace with a
counter; they are not credentials. Authentication failures and unknown routes
also get summaries. Unknown methods/paths appear only as `unknown`.

The JSON summaries omit tokens, subjects, keys, URLs, query strings, SQL text,
error messages and test output. Existing CLI diagnostics and the child process
can still print their normal output; this is not a promise to sanitize every
byte of stderr. Treat the entire process log accordingly.

Writing the summary is synchronous and serialized after the handler returns.
A slow log destination delays handler completion; no unbounded queue is added.
`duration_ns` stops before that write. Failed writes do not change the HTTP
response; the server reports their count at shutdown if stderr is usable.
A panic is rethrown and logged with status 0, meaning no successful completion
claim, not an actual HTTP status sent over the network.

## Read the timings

Each stage gives a call count and accumulated nanoseconds. Divide by 1,000,000
for milliseconds. Missing stages mean they were not measured, not that they
took zero time. These are elapsed durations, not CPU-only times.

| Stage | Boundary measured |
| --- | --- |
| authentication | Scoped authentication, including its database lookup, pool contention and comparison; not legacy-token comparison |
| db_pool | Taking one connection from the shared 16-connection pool; the storage operation keeps it until it finishes |
| db_lock | Advisory-lock SQL call, including round trip and waiting |
| fs_lock | Opening and acquiring the filesystem lifecycle lock |
| sql | Selected metadata reads/accounting/publication; publication includes validation, policy/binding checks and commit, not pure SQL engine time |
| files | FileBlobs Get/Put/Inventory/Remove, including applicable hashing and filesystem work |
| inventory | Combined metadata usage and file inventory during stats, limit changes and startup recounts (write admission before 15 October 2026) |
| fingerprint | Input discovery, content hashing and runtime probes |
| execution | Child execution and output handling |
| lookup | CLI lookup, including any remote fetch/status request |

Do not sum these into a total: inventory contains SQL and file work; publication
can contain another measured SQL operation. Authentication's pool wait is not
separately split out. Transaction startup, encoding, validation, scheduling and
other uninstrumented work can remain outside the smaller spans. The client sees
network and response-reading time too. This phase does not correlate a client
invocation and all its requests into one distributed trace.

## Repeat the local experiment

Build Receipt first with `make build`. Select a known passing, noninteractive
test command. The script creates and removes only its own temporary external
cache; it does not touch an existing `.receipt` directory. The command itself
can still have side effects. This invocation uses CodeCraft's already-installed
environment without asking uv to synchronize packages:

```sh
python3 scripts/measure_local.py \
  --repo /Users/siddharthsharma/Desktop/interview-prep/CodeCraft \
  --receipt ./receipt --repeats 5 -- \
  /Users/siddharthsharma/Desktop/interview-prep/CodeCraft/.venv/bin/python \
  -m pytest 02_string_parsing/tests/test_05_run_length_encoding.py \
  -q --tb=no -p no:cacheprovider
```

It runs five direct commands, one first Receipt run and five expected hits.
It refuses to report a hit comparison if a command fails or Receipt executes
instead. It captures but does not publish test output. It does not run `--verify`:
pytest's elapsed-time text can differ even when all assertions pass.

## Repeat the shared experiment

Use an explicitly selected disposable PostgreSQL database. The fixture creates
isolated schemas and temporary blob directories, then cleans up those fixtures.
Never point the test variable at production. With the variable set:

```sh
RECEIPT_MEASURE=1 go test -count=1 -ldflags=-linkmode=external \
  ./internal/cache -run '^TestMeasurementWorkloads$' -v
```

The external linker flag was needed for Go 1.22 on this Mac. With Go 1.27.2
installed as the default toolchain (15 October 2026), plain `go test` works. The experiment uses real
PostgreSQL credentials and loopback HTTP, stores 16 or 128 descriptions with
roughly 1 KiB outputs, and runs 1 or 4 clients. Each client makes 8 requests.
Cases cover reads, duplicate writes, alternating reads/writes, and reads started
alongside 8 dry-run collections. Natural overlap is not forced on every request;
a separate regression test holds the maintenance lock and checks cancellation.

Request logs go into a memory buffer during this experiment, not a real log
collector. It does not model log backpressure, TLS, disk-full faults, remote
networks, sustained arrival rates, new-key uploads or production-scale stores.
One-worker mixed samples alternate operations; four workers allow overlap.

## Recorded run, 9 October 2026

Raw samples: [phase-6-2026-10-09.json](measurements/phase-6-2026-10-09.json).
Host: macOS arm64, Go 1.22.1, disposable PostgreSQL 14.17 with a Unix socket.
The shared server used HTTP loopback, a 12-connection database pool and 16
admission slots. No production service or practice exercise was edited.

- CodeCraft: 15 tests passed. Median direct execution was 253 ms; a single
  Receipt miss took 592 ms; median hit was 127 ms. Five samples per repeated
  group, in fixed order, with warm OS caches. This is not a confidence interval.
- At 128 entries with four client workers, median read latency was 1.01 ms;
  median duplicate-write latency was 74.67 ms. Mean database-lock call time for
  those writes was 54.56 ms, showing substantial waiting in this workload.
- Reads started alongside collection had a 10.10 ms median at that size and
  worker count. A small payload did not prevent maintenance from delaying it.

These observations justify investigating lock hold time and inventory work
before adding more writer goroutines. They do not justify removing coordination.
The 16-entry single-reader sample was slower than the 128-entry one: these small
runs have noise and warm-up effects; they do not establish a monotonic latency
curve, a p99 estimate or a maximum supported throughput.

## Other runners

LeetCode, currently under `Desktop/interview-prep/LeetCode`, has inline Python
harnesses and no discovered uv/pytest project configuration. CodeCraft has both.
No setup was added to LeetCode for this phase.

Receipt already recognizes `go test` and probes `go env -json`. For a controlled
Go experiment, `go test -count=1 ./...` disables Go's test-result cache, not its
build cache ([Go command documentation](https://pkg.go.dev/cmd/go#hdr-Test_packages)).
The current probe is not a proof that external module replacements, native
libraries or all generated inputs have been captured.

At the time of this Phase 6 record, the next adapter work was to exercise Go's
existing path, then add
[`cargo test`](https://doc.rust-lang.org/cargo/commands/cargo-test.html), then
[`vitest run`](https://vitest.dev/guide/cli). Update, 15 October 2026: Phase 7
added a bounded `cargo test --frozen` adapter, described in [CARGO.md](CARGO.md).
Supported Cargo commands no longer need `--allow-generic`. Vitest still has no
adapter: it needs Node/package-manager identity, lockfiles, configuration,
dependencies and non-watch execution considered, and it requires
`--allow-generic`, which does not probe its resolved runtime or dependency
environment. Do not market that escape hatch as fully supported safe reuse.

This is an investigation, not a new implementation phase or a production benchmark.

the new benchmark functions, query-plan harness and generated measurements.

Host: Apple M1, macOS arm64, Go 1.27.2 (`GOEXPERIMENT` empty), PostgreSQL 14.17,

The SQL harness at `scripts/profile/query_plans.py` extracts actual DDL from Go
migrations. Its 10,000 entries and 100,000 evidence rows are synthetic, at the
default row-count limits, but far smaller in JSON width than many real manifests.
It bypasses application validation deliberately. It does not model actual store
quotas, blob I/O, network, prepared-plan selection under production data skew,
SQL write costs, physical disk reads or vacuum under churn. Index-only scans
benefit from fixture VACUUM. The candidate index is dropped with the schema;
there is no production index migration. Its reported timing improvement is for
SELECT count, not full DELETE/retention transactions.

The shared experiment uses the existing `TestMeasurementWorkloads`: 16/128
entries, 1/4 workers, 8 requests per worker, four modes, 320 HTTP requests total,
zero request failures. Request-log sinks are memory buffers. Its initial execution
overlapped the first microbenchmarks and SQL fixture preparation on the same
machine, so resource contention can affect the numbers. These samples establish
investigation targets, not clean causal speedups or p99 capacity claims.
CPU/heap profiles were collected in separate benchmark processes; short portions
of the fingerprint and decode profiling runs overlapped. The isolated `time -l`
decode run and local command experiment are additional observations, not matched
before/after optimization comparisons. OS caches were warm; the system's other
activity was not controlled.

The local experiment completed before the new screenshots/chapter were written.
No files were edited during those eleven command invocations. Its exact input
manifest was not retained, so later reruns may fingerprint different documentation
bytes. A later directory census is not an exact manifest for those samples.
Raw Go profiles and test binaries remain local under ignored `.tools`; only
textual reports and screenshots are committed. The whole-process cycle/instruction
counts include benchmark calibration; no per-function hardware counter, syscall
trace, network capture, power measurement, production RSS or cold-device test was
performed. Zero block-I/O counts in the decode-only process do not describe the
filesystem paths.

## Streaming file hashing, 18 October 2026

This follow-up implements only the `fileInput` path. The before binaries were
built from `4fe7a9b`; the after binaries use the new `hashFile` helper. Both were
built with Go 1.27.2 on the same macOS arm64 Apple M1 host. No compiler flags,
hash/key format, executable-probe logic or benchmark workload changed. The
benchmark comment changed to stop describing the old implementation as current.

The [raw comparison](measurements/streaming-2026-10-18/comparison.json) contains
all 24 benchmark process reports, 17 CLI timing/resource reports, full keys,
versions and the unabridged `/usr/bin/time -l` output. These are new matched
measurements; do not compare them directly with the earlier profiling session's
absolute times. Machine activity and sampling protocols differ.

Use `scripts/profile/compare_hashing.py` with four prebuilt binaries: the before
and after fingerprint test executables, then the before and after Receipt CLIs.
Build each version in its own checkout, keeping binaries outside the workload.
For each version, from its checkout:

```sh
go test -c ./internal/fingerprint -o /absolute/output/fingerprint.test
go build -o /absolute/output/receipt ./cmd/receipt
```

Then, from the updated checkout:

```sh
python3 scripts/profile/compare_hashing.py \
  /absolute/before/fingerprint.test /absolute/after/fingerprint.test \
  /absolute/before/receipt /absolute/after/receipt \
  .tools/streaming/comparison.json
```

The macOS-only helper executes six alternating before/after pairs per file size,
with 2,000 timed operations for 4 KiB and 200 for 8 MiB. Order reverses each pair.
It runs one process at a time; no other Receipt profiling/test workload was run
concurrently. Fixture writes are excluded from Go's benchmark timer and B/op,
but included in whole-process CPU/RSS and hardware-counter reports. Go benchmark
calibration/setup also remains in those process totals. `/usr/bin/time` rounds
CPU seconds to hundredths, making small-case CPU differences coarse. The OS
page cache is warm; background machine activity is uncontrolled. No pprof
sampling overhead was added to these timing runs.

| Metric (median of six process reports per version) | Before | After |
| --- | --- | --- |
| 4 KiB latency | 24,037 ns/op | 20,920.5 ns/op |
| 4 KiB allocations | 10,616 B/op | 4,956 B/op |
| 4 KiB process CPU, user + system | 0.050 s | 0.040 s |
| 4 KiB peak RSS | 12,034,048 bytes | 11,886,592 bytes |
| 8 MiB latency | 13,243,660.5 ns/op | 9,198,498.5 ns/op |
| 8 MiB allocations | 16,795,789.5 B/op | 33,632 B/op |
| 8 MiB process CPU, user + system | 1.965 s | 1.425 s |
| 8 MiB peak RSS | 44,408,832 bytes | 22,282,240 bytes |
| 8 MiB process cycles elapsed | 4,863,006,900 | 3,465,580,119.5 |

The allocation reduction follows directly from removing two file-sized slices.
The timing samples are noisier: the new large-file case ranged from 5.51 to
16.87 ms/op, the old from 11.55 to 15.29 ms/op. Medians favor streaming but do
not establish universal percentage gains. Whole-process cycle counts include
setup and runtime work; they are not CPU-cycle attribution to `hashFile`.

The second experiment creates an isolated Git directory with 256 × 4 KiB data
files, one 8 MiB file, `go.mod`, and a Go test: 259 files and 9 MiB of payload
excluding the two source/config files. `go test -count=1 ./...` is the wrapped
command. The old CLI writes the initial result to one external temporary cache;
eight alternating hit invocations per version reuse it. Every expected hit
skipped execution, both full `explain` keys matched, and all commands succeeded.
The exact key is stored in the raw JSON; a future run's temporary absolute path
will produce a different key, which is expected.

| Complete-hit metric (median of eight) | Before | After |
| --- | --- | --- |
| Receipt duration | 240.50 ms | 235.75 ms |
| Fingerprint stage | 183.90 ms | 175.72 ms |
| time-reported wall duration | 255 ms | 245 ms |
| time-reported user + system CPU | 0.190 s | 0.180 s |
| time-reported maximum RSS | 38,330,368 bytes | 29,417,472 bytes |

These wall durations and process resource reports have different boundaries from
Receipt stages. OS accounting can include waited-for subprocess usage; maximum
RSS is not a sum of simultaneously resident parent/child memory. The Go probe and
executable read remain unchanged. Whole-hit Receipt times ranged from 181–283 ms
before and 183–493 ms after. The small median difference does not support a
reliable whole-hit latency claim. A representative larger campaign is needed.

Compatibility evidence combines the byte-sequence argument, 32 old/new
size/permission comparisons, the existing version-one encoding test, and the
cross-version cache replay. Tests also check undersized/oversized/negative hints,
missing/deleted files, open/read failures, directories and symlinks. The size-hint
test models stale metadata; it does not force an actual concurrent edit. No new
claims cover snapshot consistency, permission/rename races, partial-progress
read failures, cold device reads, syscall counts, energy use, Windows behavior,
or every filesystem. Executable hashing remains a whole-file operation.
