# Measuring Receipt without guessing

Phase 6, implemented 9 October 2026. Diagnostics are opt-in; no exporter, external
service, dependency installation or deployment is required. These records are
not a durable audit trail and do not attribute uploads to a person.

## Find one request

Run the server with `--request-log` in addition to its normal configuration.
Each response has an `X-Receipt-Request-ID` generated by the server. Find that ID
in stderr to see the operation, status, handler duration and measured stages.
Incoming request-ID headers are ignored. IDs combine a random namespace with a
counter; they are not credentials. Authentication failures and unknown routes
also get summaries. Unknown methods/paths appear only as `unknown`.

The JSON summaries omit tokens, subjects, keys, URLs, query strings, SQL text,
error messages and test output. Existing CLI diagnostics and the child process
can still print their normal output; this is not a promise to sanitize every
byte of stderr. Treat the entire process log accordingly.

Writing the summary is synchronous and serialized after the handler returns.
A slow log destination delays handler completion; no unbounded queue is added.
`duration_ns` stops before that write. Failed writes do not change the HTTP
response; the server reports their count at shutdown if stderr is usable.
A panic is rethrown and logged with status 0, meaning no successful completion
claim, not an actual HTTP status sent over the network.

## Read the timings

Each stage gives a call count and accumulated nanoseconds. Divide by 1,000,000
for milliseconds. Missing stages mean they were not measured, not that they
took zero time. These are elapsed durations, not CPU-only times.

| Stage | Boundary measured |
| --- | --- |
| authentication | Scoped authentication, including its database lookup, pool contention and comparison; not legacy-token comparison |
| db_pool | Taking one connection from the shared 16-connection pool; the storage operation keeps it until it finishes |
| db_lock | Advisory-lock SQL call, including round trip and waiting |
| fs_lock | Opening and acquiring the filesystem lifecycle lock |
| sql | Selected metadata reads/accounting/publication; publication includes validation, policy/binding checks and commit, not pure SQL engine time |
| files | FileBlobs Get/Put/Inventory/Remove, including applicable hashing and filesystem work |
| inventory | Combined metadata usage and file inventory during stats, limit changes and startup recounts (write admission before 15 October 2026) |
| fingerprint | Input discovery, content hashing and runtime probes |
| discovery | Fresh Git/extra-input discovery; standalone/post-run Build also includes root lookup (see Git root reuse below) |
| input_files | Ordinary declared-file hashing loop (18 October) |
| executable | Command executable bytes, excluding path lookup (18 October) |
| toolchain | Non-Cargo subprocess probe, normalization and output hash (18 October) |
| execution | Child execution and output handling |
| lookup | CLI lookup, including any remote fetch/status request |

Do not sum these into a total: inventory contains SQL and file work; publication
can contain another measured SQL operation. Authentication's pool wait is not
separately split out. Transaction startup, encoding, validation, scheduling and
other uninstrumented work can remain outside the smaller spans. The client sees
network and response-reading time too. This phase does not correlate a client
invocation and all its requests into one distributed trace.

## Repeat the local experiment

Build Receipt first with `make build`. Select a known passing, noninteractive
test command. The script creates and removes only its own temporary external
cache; it does not touch an existing `.receipt` directory. The command itself
can still have side effects. This invocation uses CodeCraft's already-installed
environment without asking uv to synchronize packages:

```sh
python3 scripts/measure_local.py \
  --repo /Users/siddharthsharma/Desktop/interview-prep/CodeCraft \
  --receipt ./receipt --repeats 5 -- \
  /Users/siddharthsharma/Desktop/interview-prep/CodeCraft/.venv/bin/python \
  -m pytest 02_string_parsing/tests/test_05_run_length_encoding.py \
  -q --tb=no -p no:cacheprovider
```

It runs five direct commands, one first Receipt run and five expected hits.
It refuses to report a hit comparison if a command fails or Receipt executes
instead. It captures but does not publish test output. It does not run `--verify`:
pytest's elapsed-time text can differ even when all assertions pass.

## Repeat the shared experiment

Use an explicitly selected disposable PostgreSQL database. The fixture creates
isolated schemas and temporary blob directories, then cleans up those fixtures.
Never point the test variable at production. With the variable set:

```sh
RECEIPT_MEASURE=1 go test -count=1 -ldflags=-linkmode=external \
  ./internal/cache -run '^TestMeasurementWorkloads$' -v
```

The external linker flag was needed for Go 1.22 on this Mac. With Go 1.27.2
installed as the default toolchain (15 October 2026), plain `go test` works. The experiment uses real
PostgreSQL credentials and loopback HTTP, stores 16 or 128 descriptions with
roughly 1 KiB outputs, and runs 1 or 4 clients. Each client makes 8 requests.
Cases cover reads, duplicate writes, alternating reads/writes, and reads started
alongside 8 dry-run collections. Natural overlap is not forced on every request;
a separate regression test holds the maintenance lock and checks cancellation.

Request logs go into a memory buffer during this experiment, not a real log
collector. It does not model log backpressure, TLS, disk-full faults, remote
networks, sustained arrival rates, new-key uploads or production-scale stores.
One-worker mixed samples alternate operations; four workers allow overlap.

## Recorded run, 9 October 2026

Raw samples: [phase-6-2026-10-09.json](measurements/phase-6-2026-10-09.json).
Host: macOS arm64, Go 1.22.1, disposable PostgreSQL 14.17 with a Unix socket.
The shared server used HTTP loopback, a 12-connection database pool and 16
admission slots. No production service or practice exercise was edited.

- CodeCraft: 15 tests passed. Median direct execution was 253 ms; a single
  Receipt miss took 592 ms; median hit was 127 ms. Five samples per repeated
  group, in fixed order, with warm OS caches. This is not a confidence interval.
- At 128 entries with four client workers, median read latency was 1.01 ms;
  median duplicate-write latency was 74.67 ms. Mean database-lock call time for
  those writes was 54.56 ms, showing substantial waiting in this workload.
- Reads started alongside collection had a 10.10 ms median at that size and
  worker count. A small payload did not prevent maintenance from delaying it.

These observations justify investigating lock hold time and inventory work
before adding more writer goroutines. They do not justify removing coordination.
The 16-entry single-reader sample was slower than the 128-entry one: these small
runs have noise and warm-up effects; they do not establish a monotonic latency
curve, a p99 estimate or a maximum supported throughput.

## Git root reuse, 18 October 2026

Implementation: [chapter 14](guide/14-reuse-the-git-root.md). Baseline is unmodified
`97b833e`; candidate reuses settings' freshly discovered root only for the initial
CLI fingerprint. `Build` and post-execution root discovery stay fresh. This reduces
Git subprocesses on a hit from three to two, and on an ordinary miss from five to
four. It does not cache listings, change Git flags or skip the post-run scan.

An initial ten-sample read-only investigation in this repository measured
`git rev-parse --show-toplevel` at median 16.07 ms and `git ls-files -z --cached
--others --exclude-standard` at 20.47 ms. Output sizes were 48 and 7,583 bytes.
Python's monotonic clock surrounded each subprocess. This separates the commands,
not Git startup from its internal filesystem operations. The root calls were
measured before the listing calls, so this initial investigation is not an
alternating performance comparison. [Raw samples](measurements/discovery-2026-10-18/repository-breakdown.json).

One fewer Git process is established by an app regression test; syscall counts,
cold-device/network filesystem behavior, energy, large repositories and Windows

## Toolchain probe normalization, 18 October 2026

[Chapter 15](guide/15-measure-toolchain-probe-overhead.md) describes this deliberately
small optimization. Baseline: unmodified `4cbf0d7`. Candidate: literal scanning of
ordinary Go scratch-path flags instead of per-call regexp compilation and repeated
replacement passes. Long (>4096-byte) or invalid-UTF-8 prefixes keep the original
regexp path; the threshold is not a path-length refusal. Probe commands, fields,
JSON serialization, hashes, names and freshness are unchanged. No Python/Rust
probe optimization or result caching was implemented.

### What the measurements mean

The primary estimate is the arithmetic mean of old-minus-new Receipt duration
within each pair or group. Positive means saved time. Receipt duration includes
its own work and waiting; an external monotonic timer additionally includes the
Python launcher, `time` wrapper and process startup/exit. The JSON preserves both.
Stage durations identify where Receipt waited or worked, not CPU time in that
stage. `outside_discovery_ms` is each invocation's total minus discovery.
These paired means add exactly; independently computed medians need not.

CPU is the Python parent's change in waited-child user plus system time,
including the wrapper and waited descendants. It has finer reporting resolution
than the original experiment's hundredth-second `time` output. CPU time is not a
hardware cycle count. Peak RSS comes from macOS `/usr/bin/time -l`, in decimal MB;
it is not simultaneous whole-process-tree RAM or total allocated bytes.

For each metric the harness resamples the paired differences 5,000 times and
reports a central 95% bootstrap interval. Resampling means repeatedly drawing
from the observed data to see how the average changes. It also groups five
successive comparisons within each case/block and resamples those group means.
The tables use this latter interval to retain some short-range dependence.
There are only 12 groups for 60 comparisons and six for 30 comparisons; neither
method models all drift or establishes a 95% guarantee for other machines.
The raw JSON also records individual-pair intervals, medians, ranges, order
differences and all three block means. Controls are a check on the method, not
a correction to subtract automatically from another case's estimate.

## Git Trace2 and the macOS launcher, 18 October 2026

Research following the GC diagnosis identified two complementary tools.
[Git Trace2](https://git-scm.com/docs/api-trace2) emits internal elapsed times,
regions, command arguments and child-process events. Apple's
[System Trace guidance](https://developer.apple.com/videos/play/wwdc2026/268/)
distinguishes runnable threads waiting for CPU from blocked threads waiting for
an event. Trace2 narrows the slow interval; OS tracing investigates its cause.

We compared /usr/bin/git with the Git executable returned by xcrun --find git:
the latter was inside Xcode. Apple documents the
[/usr/bin developer-tool shims](https://developer.apple.com/library/archive/technotes/tn2339/_index.html)
that select corresponding tools inside Xcode. This comparison uses the same
Apple Git 2.54.0 version and command flags through two entry points.

The same local fixture was used: 256 × 4 KiB files plus the small Go fixture,
with no tracked input files. Each command had 60 adjacent launcher/direct pairs,
balanced by order, randomized with seed 20261018 and interleaved between root
discovery and file listing. Three warmups per command/entry point were excluded.
All 240 measured calls succeeded and each pair's output SHA-256 matched.
The traces emitted no child_start events. Results and all Trace2 events are
in the [raw comparison](measurements/git-trace2-2026-10-18/comparison.json).

| Command / entry point | Outer median | Git-reported median | Child CPU median |
| --- | ---: | ---: | ---: |
| Root query, launcher | 18.51 ms | 1.58 ms | 15.43 ms |
| Root query, direct | 7.34 ms | 1.55 ms | 5.83 ms |
| File listing, launcher | 19.51 ms | 2.80 ms | 16.54 ms |
| File listing, direct | 8.64 ms | 2.66 ms | 7.12 ms |

Paired arithmetic-mean savings were 10.93 ms for root discovery and 11.04 ms
for listing. Mean child CPU savings were 9.55 and 9.40 ms. This is exploratory
one-session evidence, with tracing enabled and warm caches; no confidence
interval or whole-Receipt benefit is established. The original rare tail did
not recur: launcher listing peaked at 26.16 ms and direct listing at 10.94 ms.
It would be incorrect to attribute the earlier 249–302 ms calls to the shim
from this experiment alone.

Git-reported duration is the final atexit event's t_abs in seconds, not Git CPU
time. The outer clock surrounds subprocess launch, output capture and waiting.
Subtracting the two includes work before Git's timing begins, process teardown
and parent overhead/descheduling. It is not an exact pure-shim timer.
Nevertheless, the matched entry-point comparison identifies substantial
routine startup overhead while Git's reported work is similar.

The local fixture resides on /dev/disk3s5 mounted at /System/Volumes/Data.
The exact commands inspect local repository metadata and the working tree;
they do not ordinarily contact a Git remote. No selected fsmonitor/untracked
cache/global-excludes overrides were found in the checked configuration.
These checks do not substitute for a packet trace, but remote round-trip
latency is not supported as the explanation here. Network mounts or custom
helpers would require separate checking in another environment.

No production Git selection, PATH or configuration changed. Direct selection
would need to respect user-selected Git and active developer-tool changes.
Calling xcrun on every operation could consume some of the saved time.

| --- | ---: | ---: | ---: | ---: |
| Root query | 244.97 ms | 233.65 ms | 5.65 ms | 5.68 ms |
| File listing | 238.99 ms | 200.94 ms | 18.55 ms | 19.50 ms |

For the listing, Start returned after 6.23 ms, first output arrived about
219.65 ms after the call began, and Wait returned at about 239 ms. Git's
read_directory region took 11.34 ms and index reading 0.013 ms.
These two reproduced outliers are primarily startup delays before Git's
instrumented execution. They do not establish whether the Apple shim, dynamic
loader, scheduling, page faults or another startup dependency caused that delay.

The [selected captures and attempt record](measurements/git-outliers-2026-10-18/startup-cases.json)
preserve PID-aligned parent timestamps, full matching Git events and GC counters.
The Git-clock origin is estimated from the final atexit event's timestamp minus
its t_abs. Parent intervals use Go's monotonic clock; alignment uses wall-clock
timestamps with microsecond precision. The arithmetic therefore differs by
microseconds and does not identify an individual kernel wait.

The first capture's first-output counter was bypassed because an embedded
bytes.Buffer exposed ReadFrom, allowing copying without calling our Write
method. Its start/wait/Trace2 measurements remain usable. The corrected
diagnostic writer owns a named buffer and records its first write; the final
harness rejects a successful nonempty output whose timestamp was not captured.

### The larger control changes the scope of the diagnosis

We then measured 500 balanced, randomized pairs through diagnostic Receipt:
1,000 Go cache hits total, five excluded warmups per version, one frozen parent
environment and seed 20261018. Both binaries use the original 97b833e baseline,
which makes three Git calls per hit. One retains normal Git selection; the other
uses the same selected Xcode Git directly. Git was resolved before measuring,
so resolution cost is excluded. No production selection policy or PATH changed.
Old entries replayed in every measured call; full keys matched at both ends.

| Diagnostic baseline metric | Launcher | Direct Git |
| --- | ---: | ---: |
| Receipt mean | 115.97 ms | 84.69 ms |
| Receipt median | 105.92 ms | 77.98 ms |
| Receipt maximum | 476.56 ms | 416.59 ms |
| Process-tree CPU mean | 104.98 ms | 79.80 ms |
| Mean elapsed per Git call | 16.95 ms | 6.70 ms |
| Maximum Git call | 144.06 ms | 52.36 ms |
| Git calls at least 200 ms | 0 / 1,500 | 0 / 1,500 |

The mean Receipt difference is 31.28 ms and CPU difference 25.18 ms in this
diagnostic baseline. Current production already removed one root query, so
this is not a measured 31 ms benefit for current main. The comparison has no
same-binary control or prespecified confidence interval and runs on a shared
host; it is an exploratory estimate. All observations remain in the
[full paired records](measurements/git-outliers-2026-10-18/paired-replays.json).

The largest launcher hit spent 371.37 ms in go env -json, using 53.39 ms of child
CPU. Its three Git calls took only 27.71, 23.18 and 22.29 ms. Receipt GC pauses
totaled 0.0995 ms. The largest direct-Git hit had ordinary Git calls of 7.89,
9.61 and 8.68 ms, but its input-file stage took 137.79 ms, executable hashing
120.65 ms and Go probe 113.59 ms. Its process-tree CPU total was 112.17 ms
versus 416.59 ms Receipt elapsed; Receipt GC pauses were 0.0363 ms.

Thus the remaining variation is not confined to Git. The stage timers combine
work and waiting; they do not by themselves distinguish disk I/O, page faults
or being descheduled during hashing. There is evidence of delays outside Git,
not evidence for one named OS cause. Direct invocation reduces routine overhead
without establishing elimination of occasional slow cache hits.

### Capture limitations and next actions

The bounded hunts stopped at the first Git call above 200 ms or 600 hits.
One unrecorded hunt found the root-query outlier at hit 116. A windowed OS
recording found the listing outlier at hit 226, but its export did not contain
the trigger PID or a covering time range. A full-recording hunt finished
600 hits with a 108.37 ms maximum Git call; its recorder stalled while stopping
and was terminated after preserving timing records. A 100 ms watchdog sampler
trial completed 600 hits with a 150.43 ms maximum; the target exited before
sampling attached, so no useful slow-call stack was obtained.

The narrower System Call Trace attempt first failed because kperf's recording
lock remained held. Restarting the user-owned Instruments helper cleared that
lock. A repeat completed 600 hits with a 116.28 ms maximum but again failed to
finalize within the harness's timeout. No usable OS attribution is claimed.
The stale diagnostic helper was stopped afterward; no system-wide recording
or benchmark process was left running. These tooling failures are recorded
rather than treated as completed kernel evidence. Raw OS data remains local.

The focused [capture harness](https://github.com/sidsharma96/receipt/blob/main/scripts/profile/capture_git_outlier.py)
records child PID, Start/Wait boundaries and first output. Its recorder has a
90-second finalization timeout; completed target calls do not imply a verified
OS recording. The optional PID filter in
[summarize_system_trace.py](https://github.com/sidsharma96/receipt/blob/main/scripts/profile/summarize_system_trace.py)
limits extracted rows to selected process IDs. The
[paired replay harness](https://github.com/sidsharma96/receipt/blob/main/scripts/profile/compare_receipt_git_paths.py)
reproduces the direct-path control:

```sh
python3 scripts/profile/capture_git_outlier.py /path/to/97b833e-source /tmp/git-startup-capture --limit 600 --threshold 200
python3 scripts/profile/compare_receipt_git_paths.py /path/to/97b833e-source /tmp/git-startup-capture/fixture /tmp/git-path-pairs
```

Use fresh output directories. The tools modify only isolated fixtures, cache
entries and diagnostic builds; detailed traces can reveal local paths.
The build overlay's direct-path branch is experimental. A production change
must preserve the user's selected Git, handle active developer-tool changes
and failures, and include resolution cost in whole-hit measurements.
Changing PATH globally would also change Receipt's recorded environment and
could legitimately change keys; that is not the optimization tested here.

The supported next optimization is to evaluate resolving the selected Git once
within an invocation. Further variance diagnosis should measure parent/child
CPU, faults, I/O counters and scheduling around Go startup and file work as well
as Git. A successful complete OS capture is still needed to assign the waiting
to a specific kernel dependency. Caching mutable toolchain probes would need a
freshness contract; these results do not justify changing it.

## Invocation-local Git selection, 18 October 2026

Current implementation: [Chapter 16](guide/16-resolve-selected-git.md) selects Git
once per run/explain invocation. It resolves Apple's exact `/usr/bin/git` launcher
through system xcrun and keeps other PATH choices. This supersedes the experimental
preselected-path proposal above; historical diagnostic results retain their scope.

The baseline is production `7ba3cfe`, which already uses two Git commands per hit.
The candidate is the production diff in this commit, with runtime resolution cost
included. Neither binary uses tracing or a build overlay. Both use Go 1.27.2 and
`-trimpath -buildvcs=false -ldflags=-linkmode=external` on Darwin arm64, Apple M1,
Git 2.54.0 (Apple Git-157). PATH selects `/usr/bin/git`; xcrun selects
`/Applications/Xcode.app/Contents/Developer/usr/bin/git`. The battery was discharging;
no thermal/performance warning was reported. Load, hashes, keys and all observations
are in the [raw record](measurements/git-selection-2026-10-18/controlled.json).

Three blocks contain 60 Go, 30 generic and 60 old/old control quartets in total.
Each quartet has order ABBA or BAAB, balanced and randomized within blocks.
There are 600 measured hits: 240 Go comparisons, 120 generic comparisons and
240 old/old calls. Three warmup pairs per case per block are excluded by design.
A pilot was interrupted after overlapping local verification was noticed; the
reported final run began after those checks finished and excluded no completed
measurement or outlier. The final schedule and sample counts were fixed in advance.
Every child receives the same inherited environment snapshot. The 256 × 4 KiB
fixture also has a tiny Go test and ignored file; binary/cache paths are external.

The primary estimate averages each label's two calls within a quartet, then
averages old minus new across quartets. The table gives arithmetic means and
95% bootstrap intervals from groups of five neighboring quartets within each

Receipt elapsed is its own total timing span, including selection. External time
also includes process launch and `/usr/bin/time`. CPU is the difference in Python's
cumulative RUSAGE_CHILDREN user+system time across the process tree, including the
timing wrapper. RSS is `/usr/bin/time -l`'s maximum resident set report: it is not
allocation volume or summed simultaneous tree memory. We did not measure hardware
cycles, energy, or physical I/O operations in this trial. Avoid claiming those
quantities from CPU milliseconds alone.

The new selection span averaged 11.004 ms (Go) and 11.340 ms (generic). Go's
file-list discovery averaged 17.724 → 7.252 ms; generic 20.222 → 7.800 ms.
The root query before fingerprint also benefits, while resolution adds cost
outside fingerprint/discovery. Go's outside-discovery difference is only 0.871 ms
with interval −0.899–3.107 ms; neither that nor the fresh probe stage establishes
an independent Go-probe improvement. Do not sum nested spans.

Go elapsed savings by block were 12.292, 11.296 and 10.440 ms. Generic savings
were 20.363, 9.998 and 10.134 ms; its first block had slower old observations.
The group interval models only some serial dependence and cannot remove shared
host scheduling, page-cache or background-process effects. The old/old interval
contains zero but remains wide. Both effect intervals favor the change in this
run; they are not guarantees for other machines or tail quantiles. Raw individual
hits, rather than quartet averages, retain the full outliers. New Go hits still
exhibited large delays. The prior OS attribution uncertainty remains unresolved.
